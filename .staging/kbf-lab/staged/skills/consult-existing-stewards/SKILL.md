# Consult existing stewards (read-only)

When you design a solution or scaffold a child agent, you ground yourself in proven shapes rather than inventing. This is a read-only grounding surface — you read exemplars and patterns; you do not modify them and you do not email anyone (that's `consult-framework-steward` / `consult-theory-mcp`).

## When to use

- Creating a submodule agent — read progenitor's `codex-steward` / `soul-first-design` patterns and a real steward as reference.
- Designing a product's orchestration/structure — read factory's parent-orchestrator shape.
- You want to confirm you're instantiating a pattern correctly, not transplanting it.

## When NOT to use

- You need an answer that requires a steward to respond — that's an active consult (`consult-framework-steward` / `consult-theory-mcp`).
- You're tempted to modify another repo's materials — out of bounds; read only.

## Inputs

- The pattern or exemplar you need to ground against.
- Read access to the corpus (factory, progenitor's `patterns/`, other stewards as available).

## Procedure

1. **Identify** the right exemplar/pattern for the question (parent-orchestration → factory; agent creation → progenitor patterns).
2. **Read** the source materials (stack layers, pattern docs) — shape, not content to copy.
3. **Extract the shape** — how identity is structured, how refusals are grounded, how boundaries are named.
4. **Instantiate, don't transplant** — apply the pattern to your case; never copy an exemplar's content wholesale.

## Output

- A grounded understanding of the pattern, applied to the current design/child-agent.

## Red flags

- Copying a steward's soul or skills wholesale instead of authoring your own (refuse).
- Modifying another repo's materials (read-only — refuse).
- Inventing a brand-new agent *kind* yourself instead of routing the catalog question to progenitor.

## After completing

- Apply the grounded shape in `design-keybank-solution` / `create-submodule-agent`.
