# theory

**The canonical Theory Cloud workspace.** `theory` is a real agent — **Theory**, a Theory Cloud
*workspace steward* — generalized from `progenitor`: same soul-first shape, same grounding-first
discipline, but where progenitor *designs* agents, Theory *integrates, operates, and — when granted
scope — authors* a theorymcp.ai namespace inside one local workspace (authoring is the get-started
on-ramp; full rigor is a formal progenitor). Clone it and it comes up as Theory on **codex**, **Claude
Code**, or **Antigravity** out of the box, carrying the skills to wire a namespace into the local
filesystem and keep the two in sync.

It is also the reference layout: **this repo is the worked example of how a Theory Cloud workspace is
configured.**

## Principle

**The namespace MCP is the source of truth.** Local files are a *materialization* of published,
route-derived metadata — never the other way around. TheoryMCP returns guidance and bytes only; the
caller reviews, writes, and applies local files. The server never writes your filesystem. Theory is
the disciplined local half of that contract.

## Layout

Authored source of truth (edit these):

- **`SOUL.md`** — Theory's 5-layer identity (one body, three host mounts).
- **`skills/<slug>/SKILL.md`** — host-neutral skills.
- **`render-hosts.sh`** — materializes the committed host layouts below from `SOUL.md` + `skills/` and
  a single `ROUTE` knob. Mirrors the theory-mcp-server ADL v2 multi-host render.

Committed materialization (regenerated by `render-hosts.sh`; works out of the box):

```
codex                        claude_code                       antigravity
.codex/                      .claude/                          GEMINI.md            (workspace rules)
  config.toml  (theorymcp)     output-styles/theory.md         .agents/
  steward.md   (= SOUL.md)     settings.json (outputStyle)       mcp_config.json    (mcp-remote bridge)
  skills/<slug>/SKILL.md       skills/<slug>/SKILL.md            skills/<slug>/SKILL.md
                             .mcp.json  (root — theorymcp)
```

The soul mounts as the system prompt on codex (`model_instructions_file`) and Claude Code (an output
style with `keep-coding-instructions: false`), and as always-on workspace rules on Antigravity (which
offers no system-prompt override). The `theorymcp` MCP server is wired per host; it ships pointed at
`https://theorymcp.ai/theorycloud/mcp` as the worked example, and `configure-namespace` repoints
it to your own namespace.

## Skills

**Setup (wire the workspace to a namespace):**
- **configure-namespace** — point `theorymcp` at your namespace route per host (codex `config.toml`,
  Claude Code root `.mcp.json`, Antigravity `.agents/mcp_config.json`), complete auth, verify.
- **setup-mcp-bridge** — configure the `mcp-remote` stdio OAuth bridge so an OAuth-incapable host
  (Antigravity) can reach a route.

**Integrate (namespace → local):**
- **discover-namespace** — always first: `describe_interface` the routed namespace; learn its tools,
  knowledge bases, installer availability, and bootstrap convention before assuming anything.
- **list-namespace-agents** — enumerate the namespace's child agents and their installability per host.
- **materialize-agent** — plan an agent's install layout, fetch the pack to disk (never through model
  context), unzip into a target project, verify every file against served checksums, write the marker.
- **verify-install** — confirm a materialization came up whole and matches the served snapshot;
  refuse to operate half-formed.
- **update-namespace-install** — compare the local install marker to the namespace's current
  published version and re-materialize only what changed.

**Author (local → namespace, Mode 3 — opt-in, gated):**

Authoring is OFF by default; it requires an explicit `grant-authoring-scope` opt-in for this
workspace, and publish is human-authorized per publish.

- **grant-authoring-scope** — the deliberate gate that flips this workspace from pull-only to
  author-capable for the connected namespace; satisfies the soul's standing refusal.
- **scope-agent-lite** — one short conversation that confirms a new agent's shape (purpose, principal,
  host profiles, invariants, ≥3 concrete refusals) before any namespace write — the reversal point.
- **author-soul** — `create_agent` + `agent_soul_upsert`; author the agent's 5-concern identity into
  the namespace, soul-first, before any skill.
- **author-skills** — `agent_skill_upsert` per skill (strict house style), only after the soul exists.
- **define-install-layout** — `agent_install_layout_upsert` per host (ADL v2, logic-less
  placeholders); the namespace renders codex/claude_code/antigravity, you do not hand-scaffold them. A
  non-built-in client (antigravity) must first be registered in the namespace install-profile catalog
  (`agent_install_profile_upsert`), and client/MCP-server names stay dash-free (underscores, like
  `claude_code`) because codex rejects a dashed MCP name.
- **validate-and-publish** — `agent_interface_validate` (mechanical gate), then
  `agent_interface_publish` (per-publish human authorization). Refuse to publish unvalidated or
  unauthorized.
- **replicate-namespace-agents** — verbatim copy of existing published agents from a source namespace
  into a target (e.g. lab → live): export → stage locally → re-upsert → validate → publish, per agent.
  Replication, not authoring — composes nothing, copies the same identity, keeps every gate.

## Start here

1. **configure-namespace** against your route (the example ships pointed at the public `theorycloud`
   namespace, so it also works as-is).
2. **discover-namespace** to ground.
3. **list-namespace-agents** to choose what to install.
4. **materialize-agent** into a target directory, then **verify-install**.
5. **update-namespace-install** to stay in sync as the namespace evolves.

## Authoring (get-started on-ramp)

Authoring is opt-in and gated. It begins with **grant-authoring-scope** (a deliberate, session-scoped
opt-in for this workspace), then shapes and writes **one agent at a time** as drafts, soul-first
(`scope-agent-lite` → `author-soul` → `author-skills` → `define-install-layout`), and publishes only
through **two gates**: a passing `agent_interface_validate` and a per-publish human authorization
(`validate-and-publish`). The same `SOUL.md` → `agent_soul_upsert`, `skills/` → `agent_skill_upsert`,
and `render-hosts.sh` template shapes → `agent_install_layout_upsert` flow *up* into the namespace —
the inverse of the integration half — so "the namespace is the source of truth" is preserved, not
contradicted.

Authoring takes two shapes: **compose-new** (the interview-driven flow above) and **replicate** — a
verbatim copy of an existing published corpus into another namespace (e.g. lab → live) via
`replicate-namespace-agents`, which composes nothing but keeps every gate, per agent.

Needing a pattern catalog, fleets, a multi-document design pipeline, cross-agent audit, API/SDK
agents, or prompt/template/lifecycle-pack authoring means **graduating to a formal progenitor** — a
separate, deliberate step you take, not something Theory becomes.

## Regenerating the host layouts

Edit `SOUL.md` and `skills/`, then run `./render-hosts.sh` to re-materialize `.codex/`, `.claude/` +
root `.mcp.json`, and `GEMINI.md` + `.agents/`. To repoint the workspace at a different namespace for
an entire team, change `ROUTE` in `render-hosts.sh` and re-run (or use `configure-namespace` for a
single host).
